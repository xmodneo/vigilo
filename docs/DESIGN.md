# Vigilo system design (V0.9)

Vigilo is a TypeScript modular monolith for **reviewed, bounded repair attempts** on public Node.js repositories. The intended path is frozen source → measured baseline → source-grounded AI diagnosis → bounded candidate → independent verification → human decision. The live V0.9 record stops at AI investigation: two real baselines completed with failing tests, but no accepted diagnosis or AI-generated patch followed. [Historical evidence](evidence/historical/README.md) separates implemented controls from observed outcomes.

## Components and data flow

1. **Web and identity.** A Next.js application uses Better Auth for the owner session and GitHub OAuth/App integration. The selected repository must be public. A frozen execution profile binds the GitHub installation, repository, revision, runtime, package scripts, and source identity. Owner-triggered handoffs retain authentication, origin/CSRF, workspace ownership, and reviewed-authority checks. The old self-service Start Repair POST is closed.
2. **Reviewed staging.** A local owner reviews a canonical plan bound to one release SHA, actor, public fixture, objective, provider-account identities, source checkpoint, expiry, and fixed budgets. PostgreSQL staging locks global execution and workspace state, then atomically creates one run, intent/event, pending checkpoint, one account grant, five operation grants, and one inert baseline PgBoss job. No provider starts at enqueue time.
3. **Queue and workers.** PostgreSQL contains application records and PgBoss jobs. A separately invoked exact-job worker validates the queue, real job ID, full parent binding, frozen revision, release, grants, and PostgreSQL clock before claiming that job. Each phase exits after its one target. The general multi-queue worker is not needed for these reviewed handoffs. Job leases, ownership tokens, heartbeats, and terminal events fence concurrent or lost workers.
4. **External authority.** An account grant and category grant set separate ceilings for Gemini investigation, Gemini candidate generation, baseline Sandbox, verification Sandbox, and one repair-loop iteration. Admission reserves exact amounts and records provider attempts, a lease, and a fence. Expiry, revocation, scope, provider identity, and lease ownership are rechecked before transport. Ambiguous on-wire outcomes remain consumed and block unsafe replay. The budget is an application-side bound, not a monetary guarantee.
5. **Frozen-source baseline.** The worker reconstructs the approved public commit into a fresh Vercel Sandbox and checks its manifest. Dependency installation gets a narrow npm-registry allowance. Before repository typecheck/build/tests, the worker switches networking to `deny-all` and reads back the policy in the same session. It records phase exit codes, source-integrity facts, and stop/delete/lookup-absent cleanup.
6. **Investigation and later stages.** A context worker indexes only bounded, allowed paths at the frozen commit and uses scoped read-only GitHub access. Gemini sees untrusted objective/source data through four tools: path listing, file read, text search, and sanitized baseline summary. Six model turns may use tools; a seventh is reserved for a tool-free JSON-schema conclusion. Only a completed `diagnosis_found` result can feed candidate generation and the repair loop. Candidate files are intended to be frozen and reconstructed with the pristine base in a **different** Sandbox for independent verification before human review. These later live steps were not reached in V0.9.

## Five tradeoffs and failure modes

| Design choice | Benefit | Cost or failure mode |
| --- | --- | --- |
| Owner-reviewed, expiring grants | A queue entry cannot silently authorize provider spend; release and provider scope are explicit. | Human review can outlast the grant. Attempt 1 expired before Gemini execution, requiring a fresh reviewed run rather than extending history. |
| Exact-job one-shot workers | Claims only the named job and leaves downstream jobs inert. | More operator steps and approval handoffs; an absent general worker can make broad readiness report unavailable even when an exact handoff is valid. |
| Commit- and manifest-bound source | Baseline and context refer to the same immutable public input. | A changed repo/profile needs a new review and cannot reuse old evidence; private repositories are unsupported. |
| Separate isolated Sandboxes | Baseline and candidate verification cannot share a mutable runtime; network policy and cleanup are checked. | Provider creation, metered transport, and cleanup can fail or become ambiguous; a failed cleanup is not proof of absence. |
| Stateless, bounded Gemini turns | Every request is metered and source access stays within four audited tools. | History grows with each turn. In attempt 2, six tool turns used the available context slots; finalization returned no accepted conclusion. Raw final output was not retained, so the exact cause cannot be assigned to model behavior or parsing. |

## Evidence and operational boundaries

PostgreSQL is the durable source of run state, source checkpoints, attempt outcomes, reservations, leases, and provider-event metadata. A successful HTTP response or provider response alone is not an accepted repair. The baseline records show two real red tests under matched source and confirmed cleanup; the Gemini ledger shows seven successful provider responses, not a valid diagnosis. There is no live candidate-generation or independent green-verification evidence.

The schema ledger is forward-only through migration 0027 in the inspected local development database. Production hosting, managed backups, monitoring, real-provider restart recovery, and full publication acceptance remain unverified. Source files in this repository document implementation; the [sanitized historical package](evidence/historical/README.md) documents observed live behavior.
